# 《巷口花食铺》项目健康检查

日期：2026-09-10

## 结论

项目已经完成核心玩法 MVP 验证，并进入 Cocos / 微信小游戏产品化阶段。当前最大的风险不再是“核心循环不存在”，而是工程一致性、真实微信链路、正式美术内容量与上线合规。

建议把项目分成四个成熟度看待：

| 维度 | 当前判断 |
| --- | --- |
| Web 核心玩法 MVP | 约 85-90% |
| Cocos 技术体验版 | 约 65-70% |
| 微信真实链路 | 约 45-55% |
| 商业正式上线 | 约 35-40% |

百分比只用于表达成熟度，不是精确项目管理燃尽值。

## 已完成且应保留的能力

- 7x9 合成棋盘、生成器、体力、移动与二合升级。
- 制作台、订单、金币/经验/故事点和店铺升级。
- 本地存档、教程、今日任务、合成图谱和缺口来源提示。
- Web 与 Cocos 两套自动试玩与移动端验证思路。
- Cocos Creator 3.8.8 工程及领域/应用/平台/UI 分层。
- 微信登录、云存档适配、激励视频、分享、生命周期、埋点接口。
- 云函数 OpenID、存档 revision 冲突控制和 analytics。
- Cocos 当前生产内容池自动检查：42 单、10 配方、12 顾客。

## P0：阻塞技术体验版/上线验证

### P0-1 真实微信开发者工具与 AppID 验收

当前代码层已经具备微信能力，但缺少真实平台端到端证据。必须用测试或正式 AppID 导入开发者工具并验证首屏、教程、首单、故事单、制作、升级、前后台切换。

完成标准：形成可重复执行的微信验收记录，并把发现的问题回归到自动检查中。

### P0-2 真实云存档与多设备冲突验证

当前云函数已有 revision 冲突控制，但主要是代码级模拟。需要在微信云环境验证首次保存、覆盖、断网、重试、旧 revision、不同 deviceId、前后台切换和恢复。

完成标准：真实云环境下关键路径可复现，冲突不会覆盖更新档。

### P0-3 真实激励广告异常路径

必须验证完整观看、主动跳过、加载失败、show/load 重试、重复点击、前后台切换以及奖励幂等性。

完成标准：只有完整观看成功发放奖励，任何异常不重复发奖。

## P1：高优先级工程与产品质量

### P1-1 抽取单一共享 game-core

当前 `src/game/` 与 `wechat-client/assets/scripts/domain/` 已经发生内容差异。短期新增 `npm run domain:parity` 防止静默分叉；中期应将公共领域逻辑抽到单一 package，由 Web 与 Cocos 同时引用。

完成标准：核心类型、任务、目录、状态规则不再通过复制文件维护。

### P1-2 将 GitHub Actions 作为合并门禁

已新增 `.github/workflows/verify.yml`，PR 和 main push 执行 `npm run verify`。后续应在仓库规则中把该 Check 设置为 required，禁止红灯合并。

完成标准：main 不再依赖开发者“记得本地跑测试”。

### P1-3 正式美术资产产品化

当前 Cocos 仅有部分基础材料 PNG，Web 仍包含大量代码化图形。需要建立正式物品、菜品/礼盒、顾客、店铺阶段、按钮/UI、分享图的资产清单与替换顺序。

完成标准：首日核心流程不再依赖明显占位资产。

### P1-4 Day 1 新手体验与数据埋点闭环

围绕首次 5 分钟验证：教程完成、第一次取材、第一次合成、首单、首次制作、故事反馈、首次装修、体力不足和首次广告触发。

完成标准：关键事件有埋点名称和口径，可支持首日漏斗分析。

## P2：体验扩展与长期运营

### P2-1 顾客故事演出升级

由单句弹窗升级为更有节奏的 2-3 句对白、奖励反馈与顾客关系表达。

### P2-2 内容与收集系统

在真实首日数据验证之后，再扩高阶物品、图鉴收集、更多顾客/订单和阶段内容，避免先扩内容后验证核心留存。

### P2-3 社交与长期系统

好友互访、赠送、排行、活动等暂不应成为当前主线，等单机核心留存与微信稳定性有证据后再进入规划。

## 推荐推进顺序

```text
CI 稳定
-> 微信开发者工具真实首局
-> 真实云存档
-> 真实激励广告
-> 抽取共享 game-core
-> 正式首日美术
-> Day 1 数据漏斗
-> 再扩内容和长期系统
```

这个顺序的核心原则是：先把“能稳定交付和验证”做好，再继续扩大内容规模。
